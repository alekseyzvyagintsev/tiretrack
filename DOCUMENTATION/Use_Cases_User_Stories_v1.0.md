### US-01. Ручная загрузка файла с DataMatrix-кодами

**Как** кладовщик,
**я хочу** загрузить текстовый файл, содержащий DataMatrix-коды (по одному коду на строку),
**чтобы** система обработала коды, получила данные из «Честного знака» и сохранила их в базе.

**Критерии приёмки:**

1. ✅ Форма загрузки принимает файл в текстовом формате (`.txt`), по одному коду на строку.
2. ✅ Пустые строки в файле игнорируются и не считаются ошибкой.
3. ✅ Пробельные символы в начале и конце строки кода обрезаются перед обработкой.
4. ✅ Если файл не выбран — кнопка «Загрузить» недоступна.
5. ✅ После выбора файла отображается его имя и количество строк (кодов) в файле.
6. ✅ При нажатии «Загрузить» запускается процесс обработки с индикатором прогресса.
7. ✅ По завершении обработки отображается отчёт (см. US-07).
8. ✅ Длина одного кода — до 100 символов (по ограничению поля `qr_code`).
9. ✅ Если файл содержит код длиннее 100 символов — он пропускается с причиной «превышение длины кода».

### US-02. Выбор склада перед загрузкой

**Как** кладовщик,
**я хочу** выбрать склад перед загрузкой файла с кодами,
**чтобы** все загруженные коды были автоматически приписаны к выбранному складу.

**Критерии приёмки:**

1. ✅ Перед загрузкой файла пользователь обязан выбрать склад из выпадающего списка.
2. ✅ Список складов содержит только склады, доступные пользователю (площадки пользователя).
3. ✅ Для складов ответственного хранения (тип `oh`) рядом с названием отображается поставщик.
4. ✅ Если склад не выбран — кнопка «Загрузить» недоступна.
5. ✅ Все коды из загруженного файла получают `warehouse = выбранный склад`.
6. ✅ Если склад типа `oh` — коды также получают `supplier = поставщик склада`.
7. ✅ Выбранный склад отображается в отчёте о загрузке.

### US-03. Запрос данных в «Честный знак»

**Как** система,
**я хочу** для каждого нового кода отправить запрос в «Честный знак» через библиотеку `nechestniy_znak`,
**чтобы** получить атрибуты товара (brand, model, size, product_name) и полный ответ API.

**Критерии приёмки:**

1. ✅ Запрос отправляется только для кодов, которых нет в базе (не дубликатов).
2. ✅ Полный ответ «Честного знака» сохраняется в поле `honest_sign_data` (JSONField) записи `TireCode`.
3. ✅ При ошибке API «Честного знака» (таймаут, 5xx, недоступность) — код пропускается, причина «ошибка Честного знака».
4. ✅ При ошибке код остаётся в логе загрузки со значением кода и текстом ошибки.
5. ✅ Повторный запрос в «Честный знак» для уже существующего в базе кода не отправляется (дедупликация).
6. ✅ Процесс загрузки продолжается после ошибки для следующего кода (не прерывается).

### US-04. Парсинг атрибутов шин

**Как** система,
**я хочу** распарсить из ответа «Честного знака» атрибуты шины: `brand`, `model`, `size`, `product_name`,
**чтобы** создать или найти номенклатуру и привязать код к ней.

**Критерии приёмки:**

1. ✅ Из ответа «Честного знака» извлекаются поля: `brand`, `model`, `size`, `product_name`.
2. ✅ Если хотя бы одно из полей `brand`, `model`, `size` отсутствует или пустое — код пропускается с причиной «нераспознанный».
3. ✅ Поле `product_name` необязательно: если отсутствует — `null` (fallback применяется при создании номенклатуры, см. US-05).
4. ✅ Парсинг выполняется по заранее определённым правилам маппинга полей API-ответа на атрибуты шины.

### US-05. Авто-создание номенклатуры

**Как** система,
**я хочу** автоматически создавать запись в справочнике номенклатуры при первом встреченном сочетании `brand + model + size`,
**чтобы** справочник номенклатуры заполнялся без ручного ввода.

**Критерии приёмки:**

1. ✅ Если сочетания `brand + model + size` ещё нет в `TIRE_NOMENCLATURE` — создаётся новая запись.
2. ✅ Если сочетание уже существует — новая номенклатура не создаётся, используется существующая.
3. ✅ Поле `product_name` при создании: берётся из ответа «Честного знака»; если нет — `null`.
4. ✅ Если `product_name = null`, то в интерфейсе отображается fallback-строка: `brand + model + size`.
5. ✅ `product_name` не перезаписывается при повторной загрузке кодов с тем же сочетанием.
6. ✅ Ручное редактирование `product_name` недоступно в MVP (запланировано после MVP).
7. ✅ Новая номенклатура создаётся со статусом `is_active = True`.
8. ✅ Уникальность обеспечивается ограничением `unique_together = (brand, model, size)`.

### US-06. Дедупликация кодов

**Как** система,
**я хочу** проверять каждый загружаемый код на дубликат по значению `qr_code` в базе,
**чтобы** исключить повторную загрузку и повторный запрос в «Честный знак».

**Критерии приёмки:**

1. ✅ Проверка выполняется по полю `qr_code` (unique=True) до отправки запроса в «Честный знак».
2. ✅ Если код уже существует в базе с **любым** статусом (`is_active`, `is_used`) — он пропускается.
3. ✅ Повторный запрос в «Честный знак» для дубликата не отправляется.
4. ✅ Дубликат записывается в лог со значением кода и причиной «дубликат».
5. ✅ Дубликат попадает в отчёт о загрузке в категорию «пропущено-дубликат».

### US-07. Отчёт по итогам загрузки

**Как** кладовщик,
**я хочу** увидеть отчёт по итогам загрузки файла,
**чтобы** понимать, сколько кодов успешно загружено, а сколько и почему пропущено.

**Критерии приёмки:**

1. ✅ После завершения загрузки отображается сводный отчёт:
   - Загружено и создано в базе: **N** кодов
   - Пропущено как дубликаты: **M** кодов
   - Пропущено как нераспознанные: **K** кодов
   - Пропущено по ошибке «Честного знака»: **L** кодов
2. ✅ Отчёт отображается на экране (не требует скачивания файла).
3. ✅ Дополнительно (см. US-08) отображается детальный список пропущенных кодов.

### US-08. Список пропущенных кодов

**Как** кладовщик,
**я хочу** увидеть список пропущенных при загрузке кодов с их значениями и причинами пропуска,
**чтобы** разобраться, почему коды не загрузились, и при необходимости повторить попытку.

**Критерии приёмки:**

1. ✅ В отчёте о загрузке есть раскрывающийся раздел «Пропущенные коды».
2. ✅ Для каждого пропущенного кода отображается: значение кода + причина пропуска.
3. ✅ Причины: «дубликат», «нераспознанный», «ошибка Честного знака», «превышение длины кода».
4. ✅ Список можно отсортировать по причине пропуска.
5. ✅ Список не ограничен по длине (отображаются все пропущенные коды).

### US-09. Логирование процесса загрузки

**Как** система,
**я хочу** логировать каждый шаг процесса загрузки,
**чтобы** обеспечить возможность аудита и отладки.

**Критерии приёмки:**

1. ✅ Для каждого обработанного кода в лог записывается: значение кода, результат (создан/пропущен), причина пропуска (если применимо).
2. ✅ Лог содержит временную метку для каждой операции.
3. ✅ Лог содержит идентификатор пользователя, выполнившего загрузку.
4. ✅ Лог содержит идентификатор склада, к которому загружались коды.
5. ✅ Лог доступен для просмотра администратором (формат и место хранения — на усмотрение реализации).

### US-10. Создание документа списания

**Как** кладовщик,
**я хочу** создать документ списания DataMatrix-кодов,
**чтобы** списать коды с выбранного склада.

**Критерии приёмки:**

1. ✅ Кладовщик выбирает тип документа «Списание» (`writeoff`).
2. ✅ Документ создаётся в статусе «Черновик» (не сохранён).
3. ✅ `source_platform` = площадка кладовщика (автоматически).
4. ✅ `source_warehouse` — выбирается кладовщиком из доступных складов.
5. ✅ `writeoff_platform` = площадка склада-источника (автоматически).
6. ✅ `target_warehouse = null` для документа списания.
7. ✅ `author` = текущий пользователь (автоматически).
8. ✅ Документ не виден другим кладовщикам.
9. ✅ Начальник склада видит документ (только на своей площадке).

### US-11. Создание документа выкупа

**Как** кладовщик,
**я хочу** создать документ выкупа DataMatrix-кодов,
**чтобы** выкупить коды (переписать на свой склад без перезапроса «Честного знака»).

**Критерии приёмки:**

1. ✅ Кладовщик выбирает тип документа «Выкуп» (`buyout`).
2. ✅ Документ создаётся в статусе «Черновик».
3. ✅ `source_platform` = площадка кладовщика.
4. ✅ `source_warehouse` — склад-источник (склад ОХ поставщика, с которого выкупаются коды).
5. ✅ `target_warehouse` = Основной склад площадки кладовщика (автоматически).
6. ✅ `writeoff_platform` = площадка склада-источника.
7. ✅ При выкупе приписка кодов меняется локально (на `target_warehouse`), без перезапроса «Честного знака».
8. ✅ `author` = текущий пользователь.
9. ✅ Документ не виден другим кладовщикам.

### US-12. Добавление строки в документ

**Как** кладовщик,
**я хочу** добавить строку с номенклатурой и количеством в документ,
**чтобы** указать, какие коды и в каком количестве списать/выкупить.

**Критерии приёмки:**

1. ✅ Кнопка «Добавить строку» доступна в статусах «Черновик» и «Сохранён».
2. ✅ При нажатии открывается список номенклатуры со строкой поиска.
3. ✅ Поиск выполняется по `brand`, `model`, `size`, `product_name` (частичное совпадение).
4. ✅ При выборе номенклатуры создаётся строка документа с `quantity = 1`.
5. ✅ Количество можно редактировать вручную (положительное целое число).
6. ✅ В статусе «Черновик» изменения не сохраняются в БД до нажатия «Сохранить».
7. ✅ В статусе «Сохранён» изменения сохраняются в БД при нажатии «Сохранить».

### US-13. Дубликат номенклатуры в документе

**Как** система,
**я хочу** запретить добавление дубликата номенклатуры в документ,
**чтобы** каждая номенклатура была представлена одной строкой с общим количеством.

**Критерии приёмки:**

1. ✅ При попытке добавить номенклатуру, уже присутствующую в документе, новая строка не создаётся.
2. ✅ Существующая строка с этой номенклатурой подсвечивается (визуальная индикация).
3. ✅ `quantity` в существующей строке увеличивается на 1.
4. ✅ Предлагать объединение не нужно (автоматическое увеличение).
5. ✅ Ограничение `unique_together = (document, nomenclature)` обеспечивает целостность на уровне БД.
6. ✅ Поведение одинаково в статусах «Черновик» и «Сохранён».

### US-14. Сохранение документа (черновик → сохранён)

**Как** кладовщик,
**я хочу** сохранить документ, переведя его из «Черновика» в «Сохранён»,
**чтобы** документ получил номер и сохранился в базе.

**Критерии приёмки:**

1. ✅ Кнопка «Сохранить» в статусе «Черновик» переводит документ в статус «Сохранён».
2. ✅ При сохранении документу присваивается номер (см. US-19).
3. ✅ Строки документа сохраняются в БД (создаются записи `DocumentItem`).
4. ✅ После сохранения доступны кнопки: «Добавить строку», «Сохранить» (перезаписать), «Провести», «Пометить на удаление».
5. ✅ Кнопка «Отменить» в «Черновике» сбрасывает содержимое без сохранения и закрывает форму.
6. ✅ Пустой документ (без строк) может быть сохранён (минимум 0 строк).

### US-15. Автосохранение черновика при разрыве соединения

**Как** кладовщик,
**я хочу** чтобы черновик документа автоматически сохранялся при разрыве соединения,
**чтобы** не потерять введённые данные.

**Критерии приёмки:**

1. ✅ При обнаружении разрыва сетевого соединения текущее состояние черновика сохраняется локально (в браузере/кэше).
2. ✅ При восстановлении соединения черновик восстанавливается с теми же строками и количествами.
3. ✅ Автосохранение работает только в статусе «Черновик» (до первого «Сохранить»).
4. ✅ Автосохранённый черновик не получает номер документа (номер — только при «Сохранить»).
5. ✅ Если кладовщик нажал «Отменить» — автосохранённые данные удаляются.

### US-16. Проведение документа (атомарная транзакция)

**Как** кладовщик,
**я хочу** провести документ, чтобы списать указанное количество кодов с склада,
**чтобы** коды были закреплены за документом, а счётчики обновлены.

**Критерии приёмки:**

1. ✅ Кнопка «Провести» доступна только в статусе «Сохранён».
2. ✅ Проведение — атомарная транзакция: либо все строки успешно, либо полный откат.
3. ✅ Для каждой строки проверяется: `quantity` <= количество активных кодов по позиции на складе-источнике.
4. ✅ Если хотя бы по одной строке нехватка — транзакция откатывается, возвращается ошибка с указанием позиции и доступного количества.
5. ✅ При нехватке документ остаётся в статусе «Сохранён», кладовщик корректирует количество и повторяет.
6. ✅ Если по всем строкам достаточно — выбираются старейшие активные коды по FIFO (по `created_at`, внутри дня — по `id`).
7. ✅ Выбранные коды: `is_used = True`, `is_active = False`, `document = текущий документ`, `used_at = now()`.
8. ✅ Счётчики активных кодов уменьшаются по позициям и складам.
9. ✅ Документ переходит в статус «Проведён».
10. ✅ `posted_at` = текущая дата/время.
11. ✅ Конфликт параллельного проведения: кто первым провёл — забрал коды (без резервирования).

---

### US-17. Распроведение документа

**Как** кладовщик,
**я хочу** распровести документ, чтобы вернуть коды в активные и изменить состав документа,
**чтобы** корректировать ошибки без создания нового документа.

**Критерии приёмки:**

1. ✅ Кнопка «Распровести» доступна только в статусе «Проведён».
2. ✅ При распроведении: коды документа возвращаются в активные (`is_used = False`, `is_active = True`, `document = null`, `used_at = null`).
3. ✅ Счётчики активных кодов восстанавливаются по позициям и складам.
4. ✅ Документ переходит в статус «Сохранён».
5. ✅ После распроведения доступны все кнопки статуса «Сохранён»: «Добавить строку», «Сохранить», «Провести», «Пометить на удаление».
6. ✅ Редактирование проведённого документа запрещено (до распроведения).

---

### US-18. Пометка на удаление

**Как** кладовщик,
**я хочу** пометить документ на удаление, чтобы убрать его из активной работы,
**чтобы** аннулировать ошибочно созданный документ.

**Критерии приёмки:**

1. ✅ Кнопка «Пометить на удаление» доступна в статусе «Сохранён».
2. ✅ При пометке: если документ был проведён — сначала распроведение, затем `is_deleted = true`.
3. ✅ Если документ не был проведён — просто `is_deleted = true`.
4. ✅ Документ переходит в статус «Помечен на удаление» (`marked_deleted`).
5. ✅ В статусе «Помечен на удаление» доступен только просмотр.
6. ✅ Помеченные на удаление документы не участвуют в фильтрах по умолчанию (скрыты).

---

### US-19. Нумерация документов

**Как** система,
**я хочу** присваивать документам сквозные номера при сохранении,
**чтобы** документы были однозначно идентифицируемы.

**Критерии приёмки:**

1. ✅ Номер присваивается при переходе из «Черновика» в «Сохранён» (не в «Черновике»).
2. ✅ Формат списания: `СП-ГГГГ-NNNNNN` (префикс СП, год, 6 знаков номера с нулями).
3. ✅ Формат выкупа: `ВК-ГГГГ-NNNNNN` (префикс ВК, год, 6 знаков номера с нулями).
4. ✅ Счётчик сбрасывается в начале каждого календарного года.
5. ✅ Нумерация сквозная в пределах типа документа и года.
6. ✅ Номер уникален в пределах типа и года.
7. ✅ Пример: первый документ списания 2026 года — `СП-2026-000001`.

---

### US-20. Фильтрация документов по площадкам

**Как** кладовщик или начальник,
**я хочу** фильтровать список документов по площадке-источнику документа и площадке-источнику списания,
**чтобы** быстро находить нужные документы.

**Критерии приёмки:**

1. ✅ В списке документов доступны два фильтра: «Площадка-источник документа» и «Площадка-источник списания».
2. ✅ Каждый фильтр — выпадающий список со всеми площадками.
3. ✅ Фильтры можно комбинировать (логическое И).
4. ✅ Значение «Все площадки» (по умолчанию) снимает фильтр.
5. ✅ Кладовщик видит только свои документы независимо от фильтра.
6. ✅ Начальник видит документы своей площадки (созданные на ней) при любом фильтре; чужие площадки — только чтение.

---

### US-21. Экранное отображение кодов

**Как** кладовщик,
**я хочу** увидеть коды, закреплённые за проведённым документом,
**чтобы** верифицировать, какие именно коды были списаны.

**Критерии приёмки:**

1. ✅ Кнопка/раздел «Экранное отображение кодов» доступна только в статусе «Проведён».
2. ✅ До проведения документа коды не отображаются.
3. ✅ Отображаются все коды, привязанные к документу (`TireCode.document = текущий документ`).
4. ✅ Для каждого кода отображается: текстовый код (в две строки), номенклатура (brand + model + size или product_name).
5. ✅ DataMatrix-код отображается визуально (графически), размер — сопоставим со спичечным коробком в книжном формате.
6. ✅ Коды отображаются в порядке FIFO (по дате загрузки, затем по ID).

---

### US-22. Карточка кода

**Как** кладовщик,
**я хочу** увидеть карточку конкретного кода,
**чтобы** получить полную информацию о коде и его номенклатуре.

**Критерии приёмки:**

1. ✅ Карточка кода отображает:
   - Текстовый код (в две строки)
   - Номенклатуру: производитель (brand) + модель (model) + размер (size)
   - DataMatrix-код (графическое изображение, размер ~ спичечный коробок, книжный формат)
2. ✅ `product_name` отображается, если заполнен; иначе — fallback-строка `brand + model + size`.
3. ✅ Карточка доступна из экранного отображения кодов в проведённом документе.

---

### US-23. Счётчики активных кодов

**Как** кладовщик или начальник,
**я хочу** видеть счётчики активных кодов по позициям и складам,
**чтобы** понимать, сколько кодов доступно для списания.

**Критерии приёмки:**

1. ✅ Счётчики отображают количество активных кодов (`is_active = True`, `is_used = False`) по каждой номенклатуре на каждом складе.
2. ✅ Счётчики доступны в виде таблицы/списка с группировкой по складам и позициям.
3. ✅ При проведении документа счётчики уменьшаются на количество списанных кодов.
4. ✅ При распроведении счётчики восстанавливаются.
5. ✅ Счётчик обновляется в реальном времени (или при перезагрузке страницы).
6. ✅ Начальник видит счётчики своей площадки; чужие — только чтение.
7. ✅ Кладовщик видит счётчики складов, с которых может списывать (любая площадка).

---

### US-24. FIFO-выбор кодов при проведении

**Как** система,
**я хочу** выбирать старейшие активные коды по FIFO при проведении документа,
**чтобы** обеспечить корректный порядок списания.

**Критерии приёмки:**

1. ✅ Выбор кодов выполняется по `created_at` (дата загрузки в систему) — от старых к новым.
2. ✅ Внутри одного дня — по `id` (автоинкремент) — от меньшего к большему.
3. ✅ Выбираются только коды с `is_active = True` и `is_used = False`.
4. ✅ Выбор ограничен: `nomenclature` = номенклатура строки, `warehouse` = склад-источник документа.
5. ✅ Количество выбранных кодов = `quantity` из строки документа.
6. ✅ Если доступных кодов меньше `quantity` — транзакция откатывается (см. US-16, п. 4).
7. ✅ Выбранные коды помечаются: `is_used = True`, `is_active = False`, `document = текущий`, `used_at = now()`.

---

### US-25. Права начальника склада (manager)

**Как** начальник склада,
**я хочу** иметь полный доступ к документам своей площадки и только чтение чужих,
**чтобы** контролировать операции на своей площадке без вмешательства в чужие.

**Критерии приёмки:**

1. ✅ Начальник видит все документы своей площадки (`source_platform = площадка начальника`).
2. ✅ Начальник может создавать, редактировать, проводить, распроводить, помечать на удаление документы своей площадки.
3. ✅ Документы других площадок — только чтение (просмотр без возможности редактирования).
4. ✅ Начальник видит счётчики активных кодов своей площадки (полный доступ).
5. ✅ Счётчики чужих площадок — только чтение.
6. ✅ Начальник может управлять пользователями (см. US-28).

---

### US-26. Права кладовщика (storekeeper)

**Как** кладовщик,
**я хочу** видеть и редактировать только свои документы,
**чтобы** не мешать другим кладовщикам и работать в своём контуре.

**Критерии приёмки:**

1. ✅ Кладовщик видит только документы, автором которых он является (`author = текущий пользователь`).
2. ✅ Чужие документы кладовщику не видны (не отображаются в списке).
3. ✅ Кладовщик не может редактировать чужие документы.
4. ✅ Кладовщик не может управлять пользователями.
5. ✅ Кладовщик может создавать документы списания и выкупа.
6. ✅ Кладовщик может загружать коды (см. US-01).

---

### US-27. Списание с чужой площадки

**Как** кладовщик,
**я хочу** списать коды с чужой площадки (не своей),
**чтобы** выполнить межплощадочное списание.

**Критерии приёмки:**

1. ✅ Кладовщик может выбрать склад-источник с любой площадки (не только своей).
2. ✅ Документ создаётся на имя кладовщика (`author = кладовщик`).
3. ✅ `source_platform` = площадка кладовщика.
4. ✅ `writeoff_platform` = площадка склада-источника (может отличаться от `source_platform`).
5. ✅ Счётчики активных кодов уменьшаются у площадки-источника списания (`writeoff_platform`).
6. ✅ Кладовщик видит счётчики склада-источника (чужой площадки) для планирования списания.
7. ✅ Начальник чужой площадки видит этот документ в режиме чтения (документ затрагивает его площадку как `writeoff_platform`).

---

### US-28. Управление пользователями

**Как** начальник склада,
**я хочу** создавать и управлять учётными записями пользователей (кладовщиков и начальников),
**чтобы** назначать роли и привязывать пользователей к площадкам.

**Критерии приёмки:**

1. ✅ Только начальник (`manager`) имеет доступ к управлению пользователями.
2. ✅ Начальник может создать пользователя с указанием:
   - Имя / логин
   - Роль: `manager` (начальник) или `storekeeper` (кладовщик)
   - Площадка (привязка к `Platform`)
3. ✅ Начальник может изменить роль или площадку пользователя.
4. ✅ Начальник может деактивировать пользователя (без удаления).
5. ✅ Кладовщик не имеет доступа к управлению пользователями.
6. ✅ Пользователь без площадки (`platform = null`) не может создавать документы.
