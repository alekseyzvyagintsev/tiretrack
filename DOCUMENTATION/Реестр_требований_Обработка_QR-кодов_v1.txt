--- ФТ-1.1 Ручная загрузка файла с DataMatrix-кодами ---
Приоритет: Высокий
Источник: Границы проекта, бизнес-правило 4
Описание:
  Пользователь вручную загружает текстовый файл, содержащий DataMatrix-коды
  (по одному коду на строку). Перед загрузкой пользователь выбирает склад,
  к которому будут приписаны все коды из файла. Поставщик указывается
  опционально (только для складов ОХ).
Критерии приёмки:
  - Файл читается построчно, пустые строки пропускаются.
  - Склад выбирается до загрузки. Без выбора склада загрузка недоступна.
  - Поставщик выбирается опционально, если склад имеет тип ОХ.
  - Загрузка без выбранного склада невозможна.

--- ФТ-1.2 Запрос данных в «Честный знак» ---
Приоритет: Высокий
Источник: Бизнес-правило 3, описание реализации
Описание:
  Для каждого нового кода (прошедшего дедупликацию) система отправляет запрос
  в сервис «Честный знак» через библиотеку nechestniy_znak (класс Crpt,
  метод infoFromDataMatrix). Возвращает JSON со справочными данными о товаре.
Критерии приёмки:
  - Запрос отправляется только для кодов, отсутствующих в системе.
  - Обработка ошибок «Честного знака» (таймаут, 404, невалидный код)
    реализована (унаследована от существующего решения).
  - Коды с ошибкой «Честного знака» попадают в отчёт о загрузке
    с указанием кода и типа ошибки.

--- ФТ-1.3 Парсинг атрибутов шин ---
Приоритет: Высокий
Источник: Описание реализации, бизнес-правило 1
Описание:
  Из ответа «Честного знака» парсер извлекает:
  - brand (производитель)
  - model (модель = «Модель / артикул производителя» + «Индекс нагрузки»)
  - size (ширина + отношение высоты + R + посадочный диаметр, напр. 205/55R15)
  - product_name (наименование товара)
  Если атрибут «Номинальное отношение» = «НЕ КЛАССИФИЦИРОВАНО», заменяется на «80».
Критерии приёмки:
  - Парсер корректно извлекает brand, model, size, product_name.
  - Коды с неполными атрибутами (отсутствует brand, model или size)
    помечаются как «нераспознанные» и пропускаются.
  - В отчёте о загрузке нераспознанные коды выведены отдельной категорией.

--- ФТ-1.4 Дедупликация ---
Приоритет: Высокий
Источник: Бизнес-правило 3
Описание:
  Перед отправкой запроса в «Честный знак» система проверяет наличие кода
  в базе по значению qr_code. Если код существует с любым статусом
  (активен, использован, удалён) — он пропускается, запрос не отправляется.
Критерии приёмки:
  - Дубликаты определяются по полю qr_code (точное совпадение).
  - Дубликат не отправляется в «Честный знак».
  - Дубликаты попадают в отчёт о загрузке отдельной категорией.

--- ФТ-1.5 Логирование процесса загрузки ---
Приоритет: Высокий
Источник: Решение пользователя (19.09.2026)
Описание:
  Каждый шаг обработки кода логируется: отправка в «Честный знак», парсинг,
  создание в базе, пропуск. По итогам загрузки формируется отчёт.
Критерии приёмки:
  - Отчёт содержит: загружено и создано в базе — N; пропущено как дубликаты — M;
    пропущено как нераспознанные — K; пропущено по ошибке «Честного знака» — L.
  - Список пропущенных кодов содержит значение кода и причину пропуска.
  - Лог сохраняется и доступен для просмотра после завершения загрузки.

--- ФТ-1.6 Хранение кодов ---
Приоритет: Высокий
Источник: Модель TireCode
Описание:
  Каждый успешно распознанный код сохраняется в базе со следующими атрибутами:
  - qr_code (уникальный)
  - связь с номенклатурой (FK на Tire_nomenclature)
  - склад (FK на Warehouse)
  - поставщик (FK на Supplier, опционально)
  - is_active = true
  - is_used = false
  - honest_sign_data (полный JSON ответа «Честного знака»)
  - created_at (дата загрузки в систему)
Критерии приёмки:
  - Код создаётся только при успешном парсинге всех обязательных атрибутов.
  - created_at используется для FIFO-сортировки при списании.

--- ФТ-1.7 Счётчики активных кодов ---
Приоритет: Высокий
Источник: Бизнес-правило 6, ФТ-3.6
Описание:
  Система отображает количество активных (is_active=true, is_used=false)
  DataMatrix-кодов по каждой номенклатурной позиции и по каждому складу.
  Не количество товара, а количество кодов.
Критерии приёмки:
  - Счётчик доступен в реальном времени после проведения/распроведения документа.
  - Счётчик уменьшается при проведении документа (коды помечаются использованными).
  - Счётчик восстанавливается при распроведении документа.

2. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ — НОМЕНКЛАТУРА

--- ФТ-2.1 Автоматическое создание номенклатуры ---
Приоритет: Высокий
Источник: Бизнес-правило 1, модель Tire_nomenclature
Описание:
  Номенклатурная позиция создаётся автоматически при первом встреченном
  сочетании brand + model + size. Уникальность обеспечивается констрейнтом
  unique_together (brand, model, size).
Критерии приёмки:
  - При загрузке кода с новым сочетанием brand+model+size создаётся запись
    в Tire_nomenclature.
  - При загрузке кода с существующим сочетанием — новая номенклатура не создаётся,
    код привязывается к существующей.
  - product_name заполняется из ответа «Честного знака» при создании.
  - Если «Честный знак» не вернул product_name — поле остаётся null,
    для отображения используется fallback: brand + model + size.
  - При повторной загрузке кодов с тем же brand+model+size — product_name
    не перезаписывается, сохраняется первое значение.

--- ФТ-2.2 Отображение номенклатуры ---
Приоритет: Средний
Источник: Модель Tire_nomenclature
Описание:
  В интерфейсе номенклатура отображается через product_name, если оно заполнено.
  Если product_name пусто — отображается «brand model size».
Критерии приёмки:
  - Список номенклатуры доступен при добавлении строк в документ.
  - Поиск по номенклатуре работает по brand, model, size, product_name.

3. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ — ДОКУМЕНТЫ

--- ФТ-3.1 Создание документа ---
Приоритет: Высокий
Источник: Границы проекта, бизнес-правила 5-10
Описание:
  Пользователь создаёт документ одного из двух типов:
  - Списание: склад-источник (любой, включая чужую площадку), получатель —
    «Конечный потребитель».
  - Выкуп: склад-источник — склад ОХ (поставщик), склад-получатель —
    Основной склад площадки, к которой прикреплён пользователь.
  Документ содержит:
  - author (FK на User)
  - source_platform (площадка автора документа)
  - writeoff_platform (площадка, с которой списываются коды)
  - source_warehouse (склад-источник кодов)
  - target_warehouse (склад-получатель, для выкупа — Основной склад площадки)
  - doc_type (списание / выкуп)
  - номер документа (присваивается при переходе в «Сохранён»)
Критерии приёмки:
  - Два поля площадки (source_platform и writeoff_platform) заполняются
    отдельно для возможности фильтрации.
  - При списании с чужой площадки writeoff_platform ≠ source_platform.
  - При списании со своей площадки writeoff_platform = source_platform.
  - Номер документа формата СП-2026-000001 / ВК-2026-000001
    (префикс типа + год + сквозной номер, сброс счётчика 1 января).

--- ФТ-3.2 Жизненный цикл документа ---
Приоритет: Высокий
Источник: Бизнес-правила 5-10, статусная модель
Описание:
  Статусы документа:
  1. Черновик (не сохранён) — номер не присвоен, состав редактируется.
  2. Сохранён — номер присвоен, состав редактируется.
  3. Проведён — коды закреплены, состав неизменен.
  4. Помечен на удаление — = распроведение + is_deleted=true.
  Переходы:
  - Черновик → Сохранён (кнопка «Сохранить»)
  - Сохранён → Проведён (кнопка «Провести»)
  - Проведён → Сохранён (кнопка «Распровести»)
  - Сохранён → Помечен на удаление (кнопка «Пометить на удаление»)
  - Проведён → Сохранён → Помечен на удаление (распроведение + пометка)
Критерии приёмки:
  - В статусе «Черновик» номер не отображается.
  - В статусе «Сохранён» номер присвоен и неизменен.
  - Проведённый документ не редактируется. Для изменений — распроведение.
  - Помеченный на удаление — доступен только просмотр.
  - Автосохранение черновика при разрыве соединения (сервер получает сигнал).

--- ФТ-3.3 Кнопки по статусам ---
Приоритет: Высокий
Источник: Статусная модель
Описание:
  Черновик (не сохранён):
  - «Добавить строку» — вызывает список номенклатуры со строкой поиска
  - «Сохранить» — сохраняет, переводит в «Сохранён», присваивает номер
  - «Отменить» — сбрасывает содержимое, закрывает без сохранения
  Сохранён:
  - «Добавить строку» — вызывает список номенклатуры со строкой поиска
  - «Сохранить» — сохраняет изменения
  - «Провести» — проводит документ (атомарная транзакция)
  - «Пометить на удаление» — переводит в «Помечен на удаление»
  Проведён:
  - «Распровести» — откат проводок, возврат в «Сохранён»
  - «Экранное отображение кодов» — открывает просмотр закреплённых кодов
  Помечен на удаление:
  - Только просмотр
Критерии приёмки:
  - Набор кнопок соответствует статусу документа.
  - Недоступные действия скрыты или заблокированы.

--- ФТ-3.4 Добавление строк в документ ---
Приоритет: Высокий
Источник: Решение пользователя (20.09.2026), бизнес-правило
Описание:
  При добавлении номенклатуры в документ открывается список номенклатуры
  со строкой поиска. Пользователь выбирает позицию и указывает количество.
  Дубликаты номенклатуры в одном документе запрещены.
Критерии приёмки:
  - При попытке добавить номенклатуру, уже присутствующую в документе:
    новая строка не создаётся, существующая строка подсвечивается,
    количество в ней увеличивается на 1.
  - Предложение объединения не показывается — только подсветка + увеличение.

--- ФТ-3.5 Проведение документа (атомарная транзакция) ---
Приоритет: Высокий
Источник: Бизнес-правило 7, описание алгоритма
Описание:
  При нажатии «Провести» система выполняет атомарную транзакцию:
  1. Для каждой строки: проверить, что запрошенное количество ≤ количества
     активных кодов по позиции на складе-источнике.
  2. Если хотя бы по одной строке нехватка — откатить транзакцию, вернуть
     ошибку с указанием позиции и доступного количества.
  3. Если по всем строкам достаточно — выбрать старейшие коды (FIFO),
     пометить is_used=true, привязать к документу, уменьшить счётчики.
  4. Перевести документ в статус «Проведён».
Критерии приёмки:
  - Транзакция атомарна: либо все строки проводятся, либо ни одна.
  - FIFO: выбор кодов по created_at (по возрастанию), внутри дня — по ID.
  - При нехватке документ остаётся в «Сохранён», не блокируется, не удаляется.
  - Сообщение об ошибке: позиция, запрошено, доступно.
  - Кладовщик может уменьшить количество и повторить проведение.

--- ФТ-3.6 Распроведение документа ---
Приоритет: Высокий
Источник: Бизнес-правило 8
Описание:
  При распроведении (кнопка «Распровести»):
  - Коды, закреплённые за документом, возвращаются в активные (is_used=false).
  - Счётчики восстанавливаются.
  - Документ переходит в статус «Сохранён».
  - Связь кодов с документом сохраняется (для истории).
Критерии приёмки:
  - Распроведение доступно только для проведённого документа.
  - После распроведения документ можно редактировать и провести повторно.
  - Коды возвращаются в пул активных и доступны для других документов.

--- ФТ-3.7 Пометка на удаление ---
Приоритет: Средний
Источник: Бизнес-правило 8
Описание:
  «Помечен на удаление» = распроведение (если документ был проведён) +
  установка is_deleted=true.
Критерии приёмки:
  - Доступно для статусов «Сохранён» и «Проведён».
  - Для проведённого — сначала распроведение, затем пометка.
  - Помеченный документ доступен только для просмотра.

--- ФТ-3.8 Выкуп — изменение приписки ---
Приоритет: Высокий
Источник: Бизнес-правило 9
Описание:
  При проведении документа «Выкуп» приписка кодов меняется локально:
  - warehouse меняется на Основной склад площадки пользователя.
  - supplier обнуляется.
  - Перезапрос «Честного знака» не выполняется.
Критерии приёмки:
  - После выкупа коды числятся на Основном складе площадки.
  - Счётчик Основного склада увеличивается, счётчик склада ОХ уменьшается.
  - Внешний сервис «Честный знак» не опрашивается.

--- ФТ-3.9 Фильтрация документов ---
Приоритет: Средний
Источник: Бизнес-правило 12
Описание:
  Список документов фильтруется по двум независимым параметрам:
  - Площадка-источник документа (кто создал) — source_platform.
  - Площадка-источник списания (откуда списаны коды) — writeoff_platform.
Критерии приёмки:
  - Оба фильтра работают независимо и в комбинации.
  - При совпадении площадок документ попадает в оба фильтра.

--- ФТ-4.1 Доступность экранного отображения ---
Приоритет: Высокий
Источник: Бизнес-правило 5
Описание:
  Экранное отображение кодов доступно только после проведения документа
  (коды закреплены). До проведения — недоступно, выдаётся предупреждение.
Критерии приёмки:
  - Кнопка «Экранное отображение кодов» активна только для проведённого документа.
  - Для непроведённого — предупреждение «коды не закреплены,
    перед сканированием проведите документ».

--- ФТ-4.2 Формат карточки кода ---
Приоритет: Средний
Источник: Бизнес-правило 11, уточнение пользователя
Описание:
  Карточка кода сопоставима со стандартным спичечным коробком в книжном формате.
  Содержит:
  - Текстовый код в две строки (шрифт 10pt по меркам Word)
  - Номенклатура: производитель + модель + размер (две строки)
  - DataMatrix-код (графическое изображение)
  Расположение на экране — прокрутка (скролл), без разбивки на страницы А4.
Критерии приёмки:
  - Размер карточки визуально сопоставим со спичечным коробком.
  - Текст читабелен, шрифт не мельче 10pt.
  - DataMatrix-код сканируется ТСД с экрана монитора.

5. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ — ПОЛЬЗОВАТЕЛИ И ДОСТУПЫ

--- ФТ-5.1 Роли пользователей ---
Приоритет: Высокий
Источник: Бизнес-правила 13-16, модель User
Описание:
  Две роли:
  - Начальник склада: управляет кладовщиками (добавляет/блокирует),
    видит все документы своей площадки (полный доступ),
    документы других площадок — только чтение.
  - Кладовщик: работает только со своими документами,
    может списывать коды с любой площадки.
Критерии приёмки:
  - Пользователь имеет ровно одну роль и привязку к одной площадке.
  - Начальник видит и редактирует документы своей площадки.
  - Начальник видит документы других площадок в режиме только чтения.
  - Кладовщик видит и редактирует только свои документы.
  - Кладовщик не видит документы других кладовщиков.

--- ФТ-5.2 Списание с чужой площадки ---
Приоритет: Высокий
Источник: Бизнес-правило 15
Описание:
  Кладовщик может списывать коды с любой площадки. Документ создаётся
  на имя этого кладовщика. Счётчик уменьшается у площадки-источника списания
  (writeoff_platform), а не у площадки автора (source_platform).
Критерии приёмки:
  - source_platform = площадка кладовщика.
  - writeoff_platform = площадка, с которой списаны коды.
  - Счётчик уменьшается по writeoff_platform.
  - Документ виден в фильтре по обоим параметрам.

--- ФТ-5.3 Управление кладовщиками ---
Приоритет: Средний
Источник: Бизнес-правило 13
Описание:
  Начальник склада добавляет и блокирует кладовщиков на своей площадке.
Критерии приёмки:
  - Начальник может создать учётную запись кладовщика с привязкой к своей площадке.
  - Начальник может заблокировать кладовщика (без удаления данных).
  - Кладовщик не может управлять другими пользователями.

--- ФТ-5.4 Параллельная работа без резерва ---
Приоритет: Высокий
Источник: Бизнес-правило 7
Описание:
  Система не резервирует коды. Все кладовщики видят полный остаток активных
  кодов. Конфликт обнаруживается только в момент проведения — кто первым
  провёл, тот и забрал коды.
Критерии приёмки:
  - Нет статуса «в резерве», нет таймеров резерва.
  - При нехватке кодов в момент проведения — ошибка с указанием доступного количества.
  - Документ остаётся в «Сохранён», пользователь корректирует количество.

8. МОДЕЛИ ДАННЫХ — СВОДКА
================================================================================

8.1 Tire_nomenclature (справочник номенклатуры)
  Поля:
    - brand: CharField(100) — производитель
    - model: CharField(100) — модель
    - size: CharField(50) — размер
    - product_name: CharField(100, null) — наименование из «Честного знака»
    - is_active: BooleanField(default=True)
    - created_at: DateTimeField(auto_now_add)
    - updated_at: DateTimeField(auto_now)
  Ограничения:
    - unique_together: (brand, model, size)
  Правила:
    - Авто-создание при первом сочетании brand+model+size
    - product_name не перезаписывается при повторной загрузке
    - Fallback отображения: brand + model + size при пустом product_name

8.2 TireCode (индивидуальный DataMatrix-код)
  Поля:
    - qr_code: CharField(100, unique) — значение DataMatrix-кода
    - nomenclature: FK на Tire_nomenclature (on_delete=PROTECT)
    - warehouse: FK на Warehouse (on_delete=SET_NULL, null)
    - supplier: FK на Supplier (on_delete=SET_NULL, null, blank)
    - is_active: BooleanField(default=True)
    - is_used: BooleanField(default=False)
    - honest_sign_data: JSONField(null, blank)
    - created_at: DateTimeField(auto_now_add) — дата загрузки (для FIFO)
    - used_at: DateTimeField(null, blank) — момент пометки использованным
    - document: FK на Document (on_delete=SET_NULL, null, blank)
  Правила:
    - is_used=true при проведении документа
    - is_used=false при распроведении
    - Дедупликация по qr_code (любой статус → пропуск)

8.3 Platform (площадка)
  Поля:
    - name: CharField(100, unique)
    - created_at: DateTimeField(auto_now_add)
  Правила:
    - В MVP: одна площадка «Софийская Груз»
    - Архитектура допускает множественные площадки

8.4 Warehouse (склад)
  Поля:
    - name: CharField(100, unique)
    - warehouse_type: CharField(20) — main | oh
    - platform: FK на Platform (on_delete=CASCADE, related_name='warehouses')
    - supplier: FK на Supplier (on_delete=SET_NULL, null, blank) — только для ОХ
    - created_at: DateTimeField(auto_now_add)
  Правила:
    - Склад main = Основной склад площадки
    - Склад oh = Ответственное хранение, требует указания supplier
    - В MVP: Основной склад + склады ОХ (количество поставщиков не ограничено) на площадке «Софийская Груз»

8.5 Supplier (поставщик)
  Поля:
    - name: CharField(255, unique)
    - created_at: DateTimeField(auto_now_add)
  Без изменений от существующей модели.

8.6 Document (документ)
  Поля:
    - doc_type: CharField — writeoff (списание) | buyout (выкуп)
    - number: CharField(20, unique) — формат СП-2026-000001 / ВК-2026-000001
    - status: CharField — draft (черновик) | saved (сохранён) | posted (проведён)
                           | deleted (помечен на удаление)
    - author: FK на User (on_delete=PROTECT)
    - source_platform: FK на Platform — площадка автора документа
    - writeoff_platform: FK на Platform — площадка-источник списания
    - source_warehouse: FK на Warehouse — склад-источник кодов
    - target_warehouse: FK на Warehouse — склад-получатель (для выкупа)
    - is_deleted: BooleanField(default=False)
    - created_at: DateTimeField(auto_now_add)
    - updated_at: DateTimeField(auto_now)
  Правила:
    - Номер присваивается при переходе draft → saved
    - Формат номера: префикс типа + год + сквозной номер (сброс 1 января)
    - source_platform и writeoff_platform заполняются отдельно
    - При списании со своей площадки: source_platform = writeoff_platform
    - Проведённый документ не редактируется (только через распроведение)

8.7 DocumentItem (строка документа)
  Поля:
    - document: FK на Document (on_delete=CASCADE, related_name='items')
    - nomenclature: FK на Tire_nomenclature (on_delete=PROTECT)
    - quantity: PositiveIntegerField — запрошенное количество кодов
    - created_at: DateTimeField(auto_now_add)
  Правила:
    - Дубликаты номенклатуры в одном документе запрещены
    - При попытке добавления дубликата — подсветка строки, количество +1
    - Уникальность: unique_together (document, nomenclature)

8.8 User (расширение)
  Поля:
    - platform: FK на Platform (on_delete=SET_NULL, null) — привязка к площадке
    - role: CharField — manager (начальник) | storekeeper (кладовщик)
    - is_blocked: BooleanField(default=False) — блокировка начальником
  Правила:
    - Начальник: управляет кладовщиками своей площадки
    - Кладовщик: работает только со своими документами
    - Начальник видит чужие площадки в режиме только чтения
